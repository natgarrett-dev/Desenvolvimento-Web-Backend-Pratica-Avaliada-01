1. O papel do backend na arquitetura cliente-servidor

Na arquitetura cliente-servidor, o cliente (navegador, aplicativo móvel ou outro sistema) solicita recursos e o servidor responde a essas solicitações. O backend é a parte da aplicação que roda no servidor e que o usuário nunca vê diretamente: ele concentra as regras de negócio e coordena o acesso aos dados.

As principais responsabilidades do desenvolvedor backend são:

  • Receber e interpretar requisições vindas do frontend por meio do protocolo HTTP.
  • Autenticar e autorizar usuários (quem é você? o que pode fazer?).
  • Validar dados de entrada antes de qualquer processamento.
  • Aplicar regras de negócio (calcular totais, verificar estoque, aplicar descontos).
  • Persistir e consultar dados em bancos de dados de forma segura e consistente.
  • Responder com o código de status e o corpo adequados (normalmente JSON).
  • Garantir segurança, desempenho e escalabilidade (logs, cache, limites de uso, tratamento de erros).

2. Fluxo completo de uma requisição

Passo a passo

  1. Ação do usuário: o usuário clica em um botão ou envia um formulário; o frontend monta uma requisição HTTP (ex.: POST /api/v1/usuarios).
  2. Resolução de rede: o DNS converte o domínio em endereço IP; abre-se a conexão TCP e, em HTTPS, o handshake TLS.
  3. Chegada ao servidor: um servidor web / proxy reverso (ex.: Nginx) recebe a requisição e a encaminha à aplicação.
  4. Roteamento: o framework (ex.: FastAPI) identifica qual função trata aquele método e caminho.
  5. Middlewares: autenticação, logs, CORS e limites de requisição são aplicados.
  6. Validação: o corpo e os parâmetros são verificados (tipos, formatos, campos obrigatórios).
  7. Regra de negócio: a lógica da aplicação decide o que fazer com os dados.
  8. Acesso ao banco: o backend executa consultas (diretamente ou via ORM) para ler ou gravar dados.
  9. Resposta do banco: o banco devolve os registros ou a confirmação da operação.
  10. Serialização e resposta: o backend converte o resultado em JSON e responde com um código de status (200, 201, 404...).
  11. Renderização: o frontend recebe a resposta e atualiza a interface para o usuário.

3. Como o backend processa requisições HTTP

O HTTP é um protocolo de requisição e resposta, sem estado (stateless): cada requisição carrega todas as informações necessárias para ser entendida, sem depender das anteriores.

Anatomia de uma requisição

  • Linha de requisição: método (GET, POST, PUT, DELETE), caminho e versão do protocolo.
  • Cabeçalhos (headers): metadados como Host, Content-Type e Authorization.
  • Corpo (body): dados enviados, como um JSON (presente em POST, PUT e PATCH).

Anatomia de uma resposta

  • Linha de status: versão, código e mensagem (ex.: HTTP/1.1 201 Created).
  • Cabeçalhos: Content-Type, Location, cache, etc.
  • Corpo: o recurso solicitado ou a descrição de um erro.

Ao receber a requisição, o backend a roteia, autentica, valida, executa a lógica, consulta o banco e devolve a resposta com o código de status que melhor descreve o resultado.

4. Servidor de hardware vs. servidor de software

Comparação entre servidor de hardware e servidor de software
AspectoServidor de hardwareServidor de software
Definição Máquina física (ou virtual) com CPU, memória, disco e rede, projetada para ficar ligada e atender a muitos clientes. Programa que escuta uma porta de rede e atende requisições, executando sobre o hardware.
Exemplos Servidor em rack em um data center, instância de nuvem (AWS EC2), Raspberry Pi usado como servidor. Nginx, Apache, Uvicorn, Gunicorn, Node.js/Express, PostgreSQL (servidor de banco).
Preocupações Capacidade, energia, refrigeração, redundância, conectividade. Configuração, portas, protocolos, segurança, desempenho, logs.
Relação O servidor de software executa dentro do servidor de hardware. Um mesmo computador físico pode hospedar vários servidores de software (web, aplicação e banco de dados).

5. O papel das APIs no desenvolvimento backend

Uma API (Application Programming Interface) é o contrato que define como outros sistemas conversam com o backend. Em aplicações web, é comum usar APIs REST, que expõem recursos (usuários, produtos, pedidos) por meio de URLs e dos métodos HTTP.

  • Desacoplamento: frontend web, app mobile e outros serviços consomem a mesma API.
  • Padronização: URLs, métodos, códigos de status e formatos (JSON) previsíveis.
  • Segurança: a API é o ponto único onde se controla autenticação, autorização e validação.
  • Integração: permite conectar sistemas de terceiros (pagamentos, e-mail, logística).
  • Documentação: frameworks como o FastAPI geram automaticamente a documentação OpenAPI (/docs).
